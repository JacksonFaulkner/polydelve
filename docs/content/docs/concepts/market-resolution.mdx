## Resolution outcomes

Every contract has one of three independent win conditions, checked by `scripts/resolve_contracts.py`:

- **CVE win** — a new CVE with `cvss_score >= cvss_threshold` was published (per `cve_history`) after the contract was created (requires `cvss_threshold` set).
- **EPSS win** — `epss_history` recorded a score `>= epss_threshold` after `created_at` (requires `epss_threshold` set).
- **MAL win** — a non-withdrawn MAL advisory was published for the package after `created_at`.

Any one of these triggers a **won** contract; the deadline passing with none met resolves it **expired**, with no payout.

## How resolution is triggered

`resolve_contracts.py` does not poll OSV live per contract. It reads from tables already populated by upstream ETL jobs:

- `cve_history` — populated by the `cve` job (OSV bulk data)
- `epss_history` — populated by `epss-history` / daily `epss` refresh
- `mal_advisories` — populated by the `mal` job

For each open contract, it checks these tables for a qualifying row created after the contract's `created_at`. Won contracts get `status='won'` and `schmeckles += max_payout`; expired contracts get `status='expired'` with no payout.

## Timing and cadence

Resolution runs via `make resolve-contracts`, invoked as part of the daily ETL cycle. The scheduled Fargate task (EventBridge Scheduler) runs at **9am, 12pm, and 5pm ET** — not on a fixed interval. Contracts are not resolved in real time; there is a lag between an underlying advisory/score update landing in the database and resolution being recorded.

EPSS and CVE data refresh independently of resolution (see [Vulnerability Tracking](/docs/concepts/vulnerability-tracking)).

## Edge cases

<Accordions>

<Accordion title="Multiple qualifying conditions">
If a contract has both `cvss_threshold` and `epss_threshold` set, either one alone is sufficient to resolve YES — they are not both required.
</Accordion>

<Accordion title="Disputed or withdrawn advisories">
The system does not automatically re-open or reverse a resolved contract — resolution is final at the time the job runs.
</Accordion>

<Accordion title="Package removed from tracking">
If a package is removed from Polydelve's tracked universe after a contract opens, the contract continues to run against the last known data until the deadline.
</Accordion>

<Accordion title="Data lag">
Upstream sources (OSV, EPSS bulk file, MAL advisories) can lag their own publish times by hours to days depending on ETL cadence. Resolution is always based on Polydelve's ingested tables, not a live upstream call.
</Accordion>
